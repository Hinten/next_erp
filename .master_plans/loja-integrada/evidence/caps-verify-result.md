# Loja Integrada, Phase 0: capability verification record

Status: Phase 0 evidence. Date: 2026-10-07. Scope: the `MARKETPLACE_TIPO_CAPS` row for Loja Integrada (LI).

## 1. Provenance

On 2026-10-07 each of the 27 capability fields of the proposed LI row was handed to an independent skeptic agent. The skeptic was told to refute the survey claims against the official LI OpenAPI spec (v2, 76 paths, 25 tags, `https://api-docs.lojaintegrada.com.br/openapi/API-Loja-Integrada.json`) and the LI help center (`ajuda.lojaintegrada.com.br`). Where the skeptic needed it, it also read the legacy code, which is cited here only as "legacy code".

- Result: 25 of 27 fields held (`held: true`). 2 were corrected (`held: false`):
  - `kitVirtual`: the surveys said `desconhecido`; the spec shows no composition resource, so the value is `nao`.
  - `rastreio`: 3 of 4 surveys said `push`; the field means inbound tracking, and the webhook is not a reliable tracking feed, so the value is `pull`.
- Several held fields still had claims refuted or sharpened (recorded in the caveats). Examples: `auth` (the survey value `token-longo` is not a protocol; `api-key` is), `importarPedido`, `importarPagamento`, `etiqueta`, `enviarNfe`.
- A completeness critic then read all 27 verdicts and the surveys. It raised 11 contradictions and 8 gaps; Section 3 and Section 4 record how each was settled.
- No LI endpoint was called. All evidence is documentary (spec, help center, public web pages). Every "live probe" below is a proposal that still needs a real paid-plan LI test store and credentials.
- Notes on the legacy code are kept in the operator's private notes and are not ported into this record. The legacy client authenticates with the chave_api + aplicacao combination. The owner confirmed on 2026-10-07 that the legacy integration works; the credential it uses is most likely an old-model application key that LI may refuse at any time (see the re-verification section at the end of this record).
- The two LI stores are not named; only "the two LI stores" is used.

Citation convention: `spec <METHOD> <path>`, `spec tag <Tag>`, `spec info`; help-center articles by URL or article number; "legacy code" for the old implementation.

Probe legend used in the table:
- **R** = read-only-probe-able: a GET with real credentials settles it, no state change.
- **W** = write-only: only a write to a store, or registering a webhook, settles it. Run on a test store, never production.

## 3. Contradictions raised by the completeness critic and how they were settled

The critic read all 27 verdicts against the surveys and raised 11 contradictions. The decision column is what the master plan must follow.

1. **Order key (numero vs internal id).**
   - Conflict: `importarPedido` said the GET path takes the order `numero`; `rastreio` said to key on the internal `id`.
   - Settled by Gap 1: the canonical key is `numero`. Every REST example uses `numero` as the path value and resource URI. The internal `id` appears only in the webhook body. The `rastreio` instruction was a conflation: the id that docs name for the tracking write is the SHIPMENT id (`envios[].id`). The `rastreio` caveat about keying on the internal id is dropped.
   - Still open: whether GET with the internal id 404s or hits another order (treat as unsupported).

2. **Payment fields `boleto_url`, `pix_code`, `pix_qrcode`.**
   - Conflict: the `importarPagamento` verdict said survey B was wrong that the spec carries them.
   - Settled by the critic's direct spec query: `boleto_url` and `pix_code` are in the response schema of PUT /v1/pedido/{pedido_id}, typed null, and absent from GET. Survey B cited the PUT echo, which is correct. Decision: documented but PUT-only; treat as optional. The row value (`sim`) is unchanged.
   - Still open: whether today's GET returns them.

3. **Parent/child discovery (`filhos`).**
   - Conflict: `importarAnuncio` said `filhos` is untyped and unverified.
   - Settled: `filhos` is present in spec examples of POST /v1/produto, GET /v1/produto, PUT /v1/produto/{id} and GET /v1/produto/{id}. Discovery through `filhos` and `pai` is documented in examples; the `importarAnuncio` row comment and caveat are corrected. A live check of the real shape remains.

4. **The 2026-10-05 discontinuation of the old "chave de aplicação".**
   - Conflict: `auth` read it as killing an old store-generated key, while help 931152's title equates the Personal Token with "(chave de aplicação)", and the webhook article (help 9655071, 2024-07-29, which says to request a chave de aplicação first) predates the Personal Token.
   - Settled by Gap 2: help 931152 states the replacement explicitly. The store's credential is now the Personal Token; "chave de aplicação" now identifies only integrators and partner apps; the old store-level key model is discontinued from 2026-10-05. The owner confirmed on 2026-10-07 that the legacy client still works, so enforcement of the cut may be gradual (see the re-verification section). The inference that Personal-Token stores cannot register webhooks rests on a stale 2024 article and is NOT evidence either way.
   - Still open: whether PUT /webhooks/v1/*, Enviali v2 and the NF insert accept a Personal Token.

5. **Personal Token vs partner key as the preferred mode.**
   - Conflict: one survey preferred the partner pair with the Personal Token as fallback; another, the `auth` verdict and help 12542786 say the pair is for partner apps and own-store automations should use the Personal Token.
   - Settled (partly) by Gap 2: the Personal Token is the documented path for a store-owned integration (no IP list); the partner pair is the documented path for a multi-tenant integrator (mandatory IP allow-list). Which applies depends on whether the ERP integrates its own stores or many merchants. This is an operator decision, deferred to the master plan's first interview.

6. **ERP-to-LI freight model.**
   - Conflict: the `etiqueta` and `rastreio` verdicts say the repo row `FREIGHT_TIPO_CAPS.lojaIntegrada` (`marketplaceOwned: true`, `labelMode: 'fetch'`) is wrong; another survey and some repo tests keep LI as marketplace-owned; no verdict said what replaces it.

7. **`forma_envio` key shape.**
   - Conflict: the corpus's existing carrier-mapping key is `'{forma_envio.id}---{forma_envio.code}'` (GET shape: `code`, with `tipo` carrying the service display and a trailing space). The webhook shape uses `codigo`, `nome` "Envio Externo" and `tipo` null.

8. **Stock arithmetic (`quantidade_disponivel = quantidade - quantidade_reservada`).**
   - Conflict: `estoque.multiDeposito` asserted the relation; `estoque.suporte` and `estoque.protocolo` listed it as unsettled.

9. **Enviali units.**
   - Conflict: the tracking-endpoint prose says volume is in mm; spec tag Enviali says integer cm/g/centavos.
   - Settled by Gap 7: centimetres and grams; the "mm" prose is a documentation typo outvoted by five independent signals (tag text, minimum package equal to the Correios help article's cm figures, bill and estimate examples, tracking and postage examples).

    - Conflict: an earlier survey note mentioned status 529; the spec documents HTTP 429 with body codes 133/533/633.

## 4. Gap research

The critic listed 8 gaps; each was researched from the spec, the help center and public pages. Status is stated per gap.

### Gap 1. Canonical order identifier. Still open (a few live confirmations).

- Answer: the canonical key is the order `numero` (store-visible sequential integer). Use it as the pedido id seed, the webhook routing key and every write-back key.
- Evidence: every path example equals the `numero` of the same example and its resource URI (GET/PUT /v1/pedido/{id}, GET/PUT /v1/situacao/pedido/{id}). The GET order response has no top-level `id` at all. Spec GET /v1/situacao_historico/search filters by `?numero=` or `?id_externo=`. The NF `sale_number` is "o número do pedido de venda". The DCE endpoints say the value is the order number even where the parameter is named `pedido_id`.
- The internal `id` exists only in the webhook payload (and the order-creation response of POST /v1/integration/sales). Never feed it into /v1/pedido/{..}; store it as informational metadata only. `numero` is unique per store, so the conta id must be part of every key.
- The shipment key is different: PUT /v1/pedido_envio/{id} takes `envios[0].id`; the spec warns not to use the order id. `nf_id` is the NF's own id.
- Enviali bill: `order.code` is inferred to be the `numero` as a string; `order.id` is undocumented (send the same value unless a live call proves otherwise).
- Still open: R/W (a) does GET with the webhook's internal id also resolve; (b) what Enviali bill `order.id` must contain and whether it is validated against `order.code`; (c) is `numero` always integer-only; (d) PUT /v1/integration/sales/{sale_id} id-vs-number contradiction (out of scope unless we push orders into LI).

### Gap 2. Personal Token, partner key, and what a Personal Token can call. Still open.

- Answered from the docs (help 931152 updated 2026-09-22; 5360466; 12542786; spec info):
  - The Personal Token is the store-side replacement for the old store-level key; `chave_api` + `aplicacao` is now partner/integrator only.
  - Chave API: 20 characters, many allowed, never expires, cannot authenticate alone.
  - Personal Token: authenticates alone as `Basic <token>`; owner-only, shown once, up to 5 active, valid 3 months; a "Renovar" button appears one month before expiry and restarts the 3 months with the same token; unrenewed tokens are revoked automatically and cannot be recovered; the only warning is a panel notification, so a server integration learns of expiry from 401s.
  - Partner key: free form, 5-10 business days, tied to the declared IP list (a full list of production servers, workers, queues and scheduled jobs; changes need a new submission); requests from other origins are rejected. Both credentials need a paid plan.
  - The spec declares both schemes globally with no per-operation override, and says the IP restriction applies to integrator credentials; it is silent on Personal Token IP binding.
- NOT documented anywhere: whether a Personal-Token store can register webhooks (PUT /webhooks/v1/*), call Enviali v2, or use POST /v1/integration/pedido/nf, which also asks for `account_key` (the store's Chave API) in the body (a Personal-Token store may need to hand us a second secret). The best-supported reading is "yes", but only a live call settles it. Enviali also needs the store to have activated Enviali in its panel (errors 13 and 20).
- Architecture consequences (inference): Personal Token = per-store token, no static egress IP, needs an expiry tracker and a "reconectar" state; partner key = VPC connector plus Cloud NAT plus static IP for every caller. Design for push-with-poll-backstop either way.
- Still open (W unless noted): PUT /webhooks/v1/pedido with `Basic <PT>` (expect 200 "Registros afetados: 1" vs 401/403), and repeat-PUT behaviour; R: GET /enviali/v2/wallets and POST estimate with a PT from a non-registered IP; W: NF POST with a valid, wrong and missing `account_key`; R: PT from two IPs and which 429 code appears; R: confirm a store's Chave API can be sent as `account_key`.

### Gap 3. Request budget per store. Still open (limits need live reads; sizing needs operator inputs).

- Documented limits: HTTP 429 with code 633 at 100 req/min per store (`chave_api`), 533 at 3,000/min per application, 133 at 1,200/min per IP (spec info). That is 6,000 requests per hour per store. It is not stated whether a Personal Token falls in the same per-store bucket, or whether the window is fixed or sliding.
- Only ONE maximum page size is documented: GET /v1/pedido/search, limit max 50 (prose). GET /v1/produto, /v1/produto_estoque, the produto_preco list and /v1/categoria declare no max (every example shows `meta.limit` 20, so 20 is the default). `GET /v1/produto_preco/set/{ids}` (`;`-separated) has no documented id cap. The response envelope looks like a Django-Tastypie one, where a per-resource `max_limit` silently caps a larger requested limit (an inference); design rule: send `limit=N`, read back `meta.limit`, and drive paging off `meta.next` and `total_count`.
- Unit costs: order intake is 1 list call per 50 changed orders plus 1 detail GET per order change (N+1, not N+2: the fiscal identity is inline); order write-back is about 3 calls; stock is 1 PUT per child; price is 1 PUT per child; a family publish is 1 + 3N + images + image links calls (N=6, 8 images, 6 links = 33 calls; N=20 = 91 calls); reconciliation reads use the unfiltered list endpoints (product list items carry no price or stock).
- Steady-state arithmetic (hourly, averages, webhooks trusted): 500 SKUs and 50 LI orders/day about 59 req/h (1%); 2,000 SKUs and 200 orders/day about 200 req/h at page size 20 (3.3%), 102 at page size 1,000; 5,000 SKUs and 1,000 orders/day about 700 req/h (11.7%) at page size 20. The real risk is bursts: a full reprice of C products takes C/100 minutes of the whole bucket (2,000 SKUs = 20 minutes; 5,000 = 50 minutes); an initial publish of 100 families of 6 children is about 3,300 calls (about 33 minutes).
- Design recommendations (inference): one per-store token bucket (target at most 90/min, 10% reserve) shared by every queue, plus app-level and IP-level governors; priority lanes (order intake and write-back, then stock, then price, then reconcile, then publish/bulk); coalesce stock pushes per child; mirror remote ids so per-child PUTs never need a preceding GET; pick the sweep page size per store from a connect-time probe; sweep cadence 6-12 hours at page size 20.
- Still open: R: real max `limit` per resource (probe 100/500/1000, read `meta.limit`); R: max ids in `produto_preco/set`; R: bucket window type and Personal Token counting; `Retry-After` presence. Needed from the operator: SKU and family counts per store, children per family, images per family, LI and total orders per day, number of stores, egress strategy, bulk-reprice frequency.

### Gap 4. Webhook Produtos behaviour. Still open (nothing is documented).

- Not documented: whether the product hook fires on stock-only, price-only, sale-driven or our own writes (the help center says only "criado e editado"); batch size per delivery (the example body is a one-element ARRAY, so batching is possible); and the auth header on product hooks (stated only for orders; inferred from the identical `{notifyUrl, token}` body and placeholder text).
- In the only spec example, `estoque_quantidade` and `estoque_quantidade_reservada` are null although `estoque_gerenciado` is true, and the sample is dated 2023: do not use the hook as a quantity source. Stock lives in a separate resource, so it may not touch the product's `data_modificacao` or fire the hook.
- Decisions: assume echo is possible and build echo suppression (an idempotent handler that is a no-op when product state is unchanged, or a recorded `data_modificacao` fingerprint after our own PUT); treat the hook as a hint; keep a scheduled paged scan of GET /v1/produto_estoque (no filters, so no delta poll exists) as the drift backstop; the receiver must iterate arrays and be fail-closed by inference.
- Still open (all W, on a test store): register a hook, then run a stock-only PUT, a price-only PUT, a product PUT, a real sale and a manual panel edit; log headers, array length, `data_modificacao`; then DELETE the registration. Also retry/backoff, expected response code, and whether `estoque_quantidade` is ever a number.

### Gap 5. Stock reservation semantics. Still open (the push value is an inference).

- Spec examples cannot prove the relation: all 20 objects of the GET list example have `quantidade_reservada = 0`, including negative-stock rows (-2, -4, -1) whose `quantidade_disponivel` equals `quantidade` (not clamped at 0). The PUT body accepts only `quantidade`; reserved and available are read-only response fields. Spec tag Estoque defines only four stored fields.
- Help 924633 (updated 2026-09-01) and help 912137: units are RESERVED while the order is in Pedido Efetuado, Aguardando Pagamento or Pagamento em Análise (only if `gerenciado` is on); they LEAVE stock on Pedido Pago, Entregue, Em Produção, Em Separação, Pronto para Retirada; they RETURN on Pedido Cancelado or Pagamento Devolvido set manually. "Pagto Devolvido - Sem Retorno do Item" (the automatic refund default) counts as cancelled but the item does NOT return to stock. Faturado, Enviado, Chargeback, Disputa and Cancelamento Solicitado are unclassified. The spec's `aprovado/cancelado` flags agree.
- Consequence (inference, unconfirmed): if the ERP's sellable number already subtracts LI orders still in a neutral situação, then writing `quantidade = sellable` makes LI show `sellable - reservada` (double counting). To show `disponivel = sellable`, send `quantidade = sellable + reservada`, reading `reservada` just before the PUT (racy; re-GET after the PUT and log drift). Alternative: do not reserve LI neutral orders on the ERP side and push on-hand. Pick one model and do not mix.
- Still open: W/R: is PUT `quantidade` absolute gross; R: does a live list ever return `reservada > 0`; does `reservada` count parent rows; does rewriting `quantidade` re-derive `reservada`; stock effect of the unclassified situações.

### Gap 6. Corpus and deterministic ids for migration. CLOSED (resolved from the corpus; no live call needed).

All vectors use the fake conta id `CONTA1`. Reuse these formulas byte for byte at cutover; pin them in an `orderIds` unit test and assert the near-miss spellings are unequal.

**Pedido doc id** = sha256 of the UTF-8 string `"lojaIntegrada" + contaId + "-" + numero`, lowercase hex. `contaId` is the bare integração doc id (no collection path); `numero` is the LI order number rendered as a plain decimal integer. The literal `lojaIntegrada` prefix is glued to the conta id with no separator; the family resembles Mercado Livre (`mercadoLivre<contaId>-<id>`) and differs from Shopee (no literal prefix). Do not unify them. The pedido `numero` field is the decimal string. One LI order is one pedido (no pack/cart consolidation).
- Vector: contaId `CONTA1`, numero `165` -> `60fe37ac35667bf3d56a8cb3a015114133ce02dad6d7338ac5db4f421413e532`.

**Pagamento doc id** = sha256 of the UTF-8 string `"integracao/" + contaId + "-" + pagamentoId`, where `pagamentoId` is the numeric `pagamentos[].id` of the LI payload (an integer in the spec). The preimage uses the bare form `integracao/{contaId}`: NOT `documents/integracao/{id}` and no leading slash (Mercado Livre's `/documents/integracao/...` spelling would produce a different document). Path: `pedidos/{pedidoId}/pagamentos/{digest}`. There is no `-desconto` sibling in LI and no suffix; one Pagamento per `pagamentos[]` entry. Never normalise this preimage through a ref helper. A missing payment id should be treated as an error.
- Vector: contaId `CONTA1`, pagamento id `69291176` -> `39d4d6a7a8bbe3ec98fa3c0564f3c2974228ee2cc306a03ad6e6ef091b115178`.
- A wrong pagamento spelling forks every historical payment, doubles the payment total against the invoice, and on a channel where `canalDevolveTroco` is false leads to a hard SEFAZ rejection (865/866).

**Item id**: the pedido item id is stored raw as `String(item.id)` (the LI order-item id), not hashed (ML and Shopee hash theirs).

**Reference forms.** The stored value of the conta reference on `produtos/{id}/produtolojaintegrada` is the string `documents/integracao/{contaId}`. Writers use that form for every ref field; readers must accept `documents/integracao/<id>`, bare `integracao/<id>`, and native Firestore reference values. The leaf collection name is `produtolojaintegrada`. Link doc ids are NOT deterministic (import uses the LI product id as the doc id when no link exists; export creates auto ids): find links by field query (conta ref plus `id`), never by computing a doc id. `estadoPublicacao` wire codes are r/a/ep/v/p/pa/c/E.

**`statusProdutosMarketplace`** is a map on the produto doc; the key is `'<contaId>_<externalId>'` with both parts bare (conta doc id, LI numeric product id as string); the value carries `error?`, `enviarEstoque` (default true), `retries?`, `autoImport?`, `deleted?`. Companion produto fields written by LI: `marketplace[]` (`integracaoUid`, `externalId`, `externalParentId?`, `relevantData?`), `marketplaceIds[]` (external id strings), `integracoesComProduto[]` (bare conta ids). Resolve a produto from an order item through `marketplaceIds` and `integracoesComProduto`, comparing by the last path segment.

**`linksVariacoesli`** (field on `grupoDeVariacoes/{id}`) is an array of `{ name: string (LI grade name), grade_id: int, integracaoLiId: string (bare conta doc id), variationOptions: [ { li_option_id: int, li_option_name: string, arakene_variation_id: string[] (bare ids of the group's variations) } ] }`. It is used to build `/api/v1/grades/<grade_id>` (parent) and `/api/v1/grade/<grade_id>/variacao/<li_option_id>` (child) URIs. No `documents/` prefixes appear in this shape. The current schema leaves it untyped, awaiting this channel.

**Estoques subcollection**: `produtos/{produtoId}/estoques/{autoId}` (history under `historicoEstoque`); fields include `depositoOuterRef` ('documents/depositos/...'), `quantidade`, `quantidadeReservada`, `localizacao?`; available = `quantidade - quantidadeReservada`. The import creates one stock doc per (produto, deposito); the send reads the stock available at the account's configured deposit, floored at 0.

**Complete LI footprint in Firestore:**
- `integracao/{contaId}` with `tipo = 3` (pedido integration `lojaIntegrada`). It carries a per-store API credential field; there is no OAuth, no token subcollection and no webhook doc. The migration must move that credential to server-only secret storage; where is a decision for the operator.
- `integracao/{contaId}/pedManager/{autoId}`: the order-poll cursor (`lastPedidoId`, `lastTimeStamp`). Backend only. Migration: read the maximum `lastTimeStamp` per conta and seed one deterministic cursor doc in the new design; do not copy the history.
- `categorias/{categoriaId}/categorialojaintegrada/{autoId}` (`id`: string LI category id, `nome`), looked up by collection-group `id`. New docs should carry a conta reference; keep reading old ones tolerantly.
- Freight config in the `int_frete` collection (tipo `lojaIntegrada`, with an `'documents/integracao/<id>'` conta ref) and the freight `mapa` entries landing on `pedido.freteInicial`.
- Shared collections written by LI code: `pedidos/{id}` (`integracaoPedidoOuterRef` 'documents/integracao/<contaId>'), `pedidos/{id}/pagamentos/{digest}`, client addresses, and the produto fields above.
- There are no legacy webhook docs to migrate; the current official API v2 has order and product webhooks, so the new design can be push with a poll backstop.

### Gap 7. Enviali applicability. Still open (needs live calls).

- Auth: by the spec, the same two Authorization schemes apply to `/enviali/v2/*` as to `/v1/*` (same host, no per-operation override; every Enviali operation except tracking also requires an `x-correlation-id` UUID, echoed in the error body). Not documented: whether integrator credentials may spend a merchant's prepaid wallet (the wallet resolves from the credential; a third-party ERP buys Enviali labels automatically, so some credential works). The store must have Enviali activated (errors 13 and 20). Free plans have only Correios PAC/SEDEX.
- Units: integer centavos, centimetres and grams (spec tag Enviali). The "mm" in the tracking prose is a documentation typo. Minimums: package 1x10x15 cm and 300 g; per-product 1x1x1 cm and 100 g. LI `/v1` product weights are decimal kg strings, so the boundary to Enviali's integer grams is where billing bugs hide; use distinct typed schemas. Wrong declared volume moves real money on the wallet afterwards.
- `paperType` (GET /enviali/v2/postage/pdf): the prose enum is `PdfA4`, `PdfZpl`, `Zpl`; the parameter example and description say `A4`. Request `PdfA4` and model the three prose values as a Zod enum until a live call settles it. Other doc defects: parameter named `ids` while prose says `id`; a cross-reference to a nonexistent `/label` path; multi-id behaviour unspecified; the 200 response is declared only as `application/pdf`. After expiry or cancellation the PDF is no longer served.
- Recognising Enviali orders: match `envios[].forma_envio.id` against the id of the GET /v1/envio entry whose `tipo` is `enviali`; `forma_envio.nome === 'Enviali'` is a weaker secondary signal. In an ORDER, `forma_envio.tipo` carries the service display with a trailing space, not the provider category; `code` is the upper-cased service slug (Enviali's own slug is lower case). The GET shape uses `{code, id, nome, tipo}`; the webhook uses `{id, codigo, nome, tipo: null}` (and the example there is a non-Enviali "Envio Externo" order). The pedido holds no postage id: correlate by tracking code or via `GET /enviali/v2/postage?search=`.
- Money-safety facts: bill recomputes the quote and fails on mismatch; validation errors fail the WHOLE batch while generation errors fail individually; the only documented idempotency guard is error 32 "Order already billed", so a timeout during bill must be reconciled with a postage search before retrying; the wallet has a concurrent-order limit (`max_concurrent_orders`), so bill can fail with 28; cancel is asynchronous and blanks the order's tracking code. Enviali pushes tracking into LI itself, so we must not overwrite it with a different code.
- Design implication (inference): the capability is per pedido. Recommended: a new freight tipo for Enviali (`labelMode: 'emit'`, quote/buy/print/track capabilities, not marketplace-owned), a user-confirmed buy action showing the quote, and a postage lookup before any bill call (this is the only "fetch" case).
- Still open: R/W: integrator credentials on `/enviali/v2/*` and who is charged; R/W: accepted `paperType` strings, the Content-Type of a `Zpl` response, multi-id `ids`; R: is Authorization required on the tracking endpoint; R: `forma_envio.code`/`tipo` values for SEDEX variants, Jadlog, Loggi and J&T; R: is the Enviali `forma_envio.id` the same across stores; R: mapping of pedido numero/id to `order.id`/`order.code`; W: is bill retry-safe.

### Gap 8. Situação 1020, custom situações and status writes. Still open.

- Situação `pagamento_devolvido_sem_retorno` (id 1020): the spec lists 16 codes in the tag prose but its GET /v1/situacao example has 15 rows and omits 1020, so the spec states no flags for it. An unverified historical copy of the catalogue lists it as `aprovado: true`, `cancelado: false`, `final: true`, `notificar_comprador: false`. That conflicts with the help center, which says the order is "considerado cancelado" (item not returned to stock) and that the buyer receives a "Pagamento devolvido" e-mail. The `aprovado/cancelado` flags look like a stock-accounting classification (neutral, approved, reproved), not a refund indicator: `pedido_chargeback` and `pagamento_em_disputa` follow the same pattern. Rule to re-derive: key every state decision off the `codigo`, never off `aprovado/cancelado` alone; treat 1018 (`faturado`), 1019 (`cancelamento_solicitado`) and 1020 as first-class codes; fall back safely on unknown codes. The state set must be an open set, not a closed enum.
- Custom situações: no evidence. The API has no create/edit/delete for situações (only GET /v1/situacao, GET/PUT /v1/situacao/pedido/{id}, GET /v1/situacao_historico/search), and the help center describes a fixed set (only e-mail templates are customisable). The 1000+ ids look like later platform-wide additions (inference).
- Does PUT enforce transitions? The spec documents no guard and no error response (the old Apiary returned 202; accept any 2xx). The spec's own history example shows an API write moving a final, cancelled order to `pedido_enviado`, and the help center says statuses can be changed manually. So `final` is advisory. Our integration must enforce its own guard: never write a situação onto an order currently in 1020, 7 (`pagamento_devolvido`), 8 (`pedido_cancelado`), 16 (`pedido_chargeback`) or 6 (`pagamento_em_disputa`); read the current situação first (or use the webhook's); write only forward shipping states (`pedido_enviado`, `pedido_entregue`, `pronto_para_retirada`). Unguarded writes can corrupt LI's own stock accounting and history (help 912137, 3482968).
- Buyer e-mails: `notificar_comprador` is a read-only attribute of each situação, and the PUT body is only `{codigo}`, so the caller cannot suppress the e-mail. It is not documented whether the API path fires the mailer as the panel does; assume yes. Per the spec example, true for ids 2, 17, 7, 3, 8, 15, 14, 11, 4 and 13; false for 1019, 1018, 16, 6 and 9. Every outbound write to 11, 14 or 13 will probably e-mail the buyer.
- Still open: R: live GET /v1/situacao (real flags of 1020, per-store extras); W: the error code and body when moving out of a final situação and idempotency of a repeat PUT; W: does an API PUT trigger the buyer e-mail, and does 1020 send one.

### Documentation provenance

The spec in use is LI's own documentation. It is served from the LI-owned subdomain api-docs.lojaintegrada.com.br, with LI response headers, and it is linked from help articles 12500189 and 5360466 (12500189 calls it the official link). The spec file was last modified on 2026-09-29, and its sha256 is byte-identical to the copy the agents worked from. Its server, https://api.awsli.com.br, is the base URL the working legacy client uses today. An older, discontinued API document hosted on Apiary (titled "Versão descontinuada") also exists; it is used only as a historical reference (for example the stock formula) and never as the primary source. The spec's own info links to the help articles are crossed (they point at each other's topics), so cite the help articles by number from this record, not through those links. The spec is also partly loose: generated schemas omit grades, pai, variacoes and filhos, and several examples contain typos, so types are written from the examples and must be verified on a test store.
